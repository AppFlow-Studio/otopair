The biggest drop-off in any app's funnel is the gap between interested and actually using. Today: user downloads app → has to create account → has to enter their car → has to figure out what to do. 4.2 Clerk on web — the magic of identity portability

Architectural unlock

Clerk identities are portable across surfaces. A user who signs up on otopair.com via Clerk's web SDK creates the same Clerk user the mobile app recognizes when they sign in. Your existing webhook → users table → mobile read flow already handles both directions. Zero new mobile code is required for continuity.

// app/layout.tsx
import { ClerkProvider } from '@clerk/nextjs';

export default function RootLayout({ children }) {
  return (
    <ClerkProvider publishableKey={process.env.NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY}>
      {children}
    </ClerkProvider>
  );
}

The flow:

  1. Web user signs up → Clerk creates a user with Clerk ID clerk_abc123
  2. Clerk webhook fires → existing handler in convex/users.ts creates a users row with clerkUserId: "clerk_abc123"
  3. User downloads app, signs in with same email → Clerk recognizes the same user ID
  4. Mobile uses api.users.getByClerkUserId({ clerkUserId: "clerk_abc123" }) → finds the row → user has all their previous setup

4.3 Vehicle onboarding flow

// app/onboard/page.tsx — sketch
import { useUser } from '@clerk/nextjs';
import { useMutation, useAction } from 'convex/react';
import { api } from '@/convex/_generated/api';

function VehicleOnboard() {
  const { user } = useUser();
  const addVehicle = useMutation(api.vehicles.addByVin);          // existing mobile mutation
  const decodeVin = useAction(api.vehicleEnrichment.decodeVin);   // existing NHTSA wrapper
  const [vin, setVin] = useState('');
  const [decoded, setDecoded] = useState(null);

  const handleVinSubmit = async () => {
    const result = await decodeVin({ vin });
    setDecoded(result);  // show "2020 BMW M550i xDrive — is this right?"
  };

  const handleConfirm = async () => {
    await addVehicle({ vin, marketing_source: 'web_onboarding' });
    router.push('/onboard/success');
  };

  // UI: VIN input + "I don't know my VIN" fallback to YMM dropdown
}

Reuse existing mutations. The only marketing-specific addition is the marketing_source flag. Fallback YMM cascading dropdowns source from your existing makes / models / trims tables.

import { useConversation } from '@elevenlabs/react';

§7 The COMBO — voice agent IS the onboarding (the unfair advantage)

Why this is uniquely OtoPair

Most marketing voice agents are FAQ bots. Yours collects intent + vehicle context + email + saves the user account, all in a natural conversation. The mobile app's first turn for this user becomes a continuation, not an onboarding.

7.1 The flow, end-to-end

VISITOR: (taps "Talk to Oto" on otopair.com) OTO: "Hey, I'm Oto — Otopair's car concierge demo. What's going on with your car?" VISITOR: "My brakes are squealing when I stop at lights." OTO: "Probably the wear indicators — the pads have a little metal tab that makes that sound when they get thin. Quick question — does it happen the first time you brake from cold, or every time?" VISITOR: "Every time." OTO: "Yeah, that's the wear indicator doing its job. You've got maybe a couple weeks to a month before they really need to be done. Brake pad replacement on most cars runs $150-$300 depending on the model. What kind of car?" VISITOR: "2020 BMW M550i." OTO: "Nice — German performance pads run a bit more, maybe $250-$400 with OEM. Want me to set you up with a $25 credit you can use when you book the service through Otopair? Just need an email — I'll have your car and what we just talked about ready when you open the app." VISITOR: "Yeah, sure. it's me@example.com." (agent fires save_warm_account tool) OTO: "Got it. Check your email — there's a one-tap link to claim your account and download the app. Your M550i and the brake context will be there. Anything else I can help with?"

7.2 What happened in the backend

  1. Voice agent collected: email, vehicle (year/make/model), symptom, recommended service, cost estimate
  2. Agent fires save_warm_account tool → webhook on Convex httpAction
  3. Webhook creates a Clerk user with the email (Clerk handles email magic-link)
  4. Webhook creates a Convex users row with marketing_acquired: true
  5. Webhook creates vehicles + vehicle_owners rows with YMM
  6. Webhook creates a marketing_leads row linked via converted_to_user_id
  7. Webhook seeds a conversation_facts entry — when user opens app, mobile Oto's getCrossConversationMemory already has context
  8. Webhook fires email magic link via Clerk
  9. User taps email link → /onboard/success → SMS deep-link to App Store
  10. User opens mobile app → Clerk recognizes them → vehicles + credit + diagnostic context all already there
End result

The user's FIRST mobile-app experience is "wow, it already knows my car and remembers what I asked about". That's not onboarding — that's continuity. No competitor has this because no competitor has both (a) a voice agent and (b) the same Clerk+Convex stack on mobile and web.

7.3 The save_warm_account tool — ~80 lines of glue

// convex/marketingWarmAccount.ts
export const saveWarmAccount = httpAction(async (ctx, request) => {
  const {
    email, vehicle, symptom, recommended_service,
    estimated_cost_range, conversation_id, consent_marketing,
  } = await request.json();

  // 1. Create Clerk user (returns clerk_user_id)
  const clerkUserId = await ctx.runAction(internal.clerk.createUserByEmail, { email });

  // 2. Create Convex users row
  const userId = await ctx.runMutation(internal.users.createMarketingAcquired, {
    clerkUserId, email,
    marketing_acquired: true,
    marketing_acquired_at: Date.now(),
    marketing_acquired_source: 'voice_demo',
  });

  // 3. Resolve / create vehicle row
  const vehicleConfig = await ctx.runQuery(api.vehicleConfigs.findByYMM, vehicle);
  const vehicleId = await ctx.runMutation(internal.vehicles.createForUser, {
    user_id: userId,
    vehicle_config_id: vehicleConfig?._id,
    year: vehicle.year,
    metadata: { make: vehicle.make, model: vehicle.model, trim: vehicle.trim },
    marketing_source: 'voice_demo',
  });

  // 4. Link vehicle to user
  await ctx.runMutation(internal.vehicleOwners.create, {
    user_id: userId, vehicle_id: vehicleId,
    is_primary: true, added_at: Date.now(),
  });

  // 5. Seed conversation_facts so mobile Oto has context on first turn
  if (symptom && recommended_service) {
    await ctx.runMutation(internal.oto.memoryEditing.recordSeedFact, {
      user_id: userId, vehicle_id: vehicleId,
      payload_text: `User reported "${symptom}" during web voice demo; recommended ${recommended_service}, estimated ${estimated_cost_range}.`,
      written_by: 'marketing_web',
    });
  }

  // 6. Issue $25 credit
  await ctx.runMutation(internal.credits.issueWelcomeCredit, {
    user_id: userId, amount_cents: 2500,
    reason: 'marketing_voice_demo_signup',
  });

  // 7. Send magic-link email
  await ctx.runAction(internal.clerk.sendMagicLink, { email });

  // 8. Mark lead as converted
  await ctx.runMutation(internal.marketingLeads.markConverted, {
    voice_conversation_id: conversation_id,
    converted_to_user_id: userId,
  });

  return new Response(JSON.stringify({
    ok: true, user_id: userId, next_step: 'magic_link_sent',
  }), { status: 200 });
});
