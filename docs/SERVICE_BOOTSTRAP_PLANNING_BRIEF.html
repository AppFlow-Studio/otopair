The assignment

What this bootstrap should solve

Today, catalog definitions are split across a canonical snake-case service seed, legacy seeds, migrations, and live deployment data. A new deployment cannot currently reach a known-good service state through one reliable command.

23 Bookable services

The canonical service catalog used by mobile and web booking surfaces.

13 Active generic options

Rows used by four services through the shared option picker.

1 Operator command

A single internal bootstrap entry point with explicit results and verification.

This artifact changes no backend data. It proposes what a future seed function would do after Daniel and Temur agree on scope and replacement rules.

Current evidence

What is true today

Temurbek deployment

  • 23 active service rows.
  • 60 total service_options rows.
  • Only 13 option rows point to the current 23-service catalog.
  • The other 47 rows point to deleted legacy service IDs and should not be reproduced.
  • 8 category rows exist; 23 services reference 7 of them. The eighth, “Maintenance,” is unreferenced.

Current repository

  • convex/seeds/seedServices.ts is the snake-case catalog source.
  • It currently skips if any service already exists.
  • Its category model has moved to four consolidated booking groups.
  • The 13 active options are not part of that fresh-deployment seed.
  • Legacy root seeds use incompatible kebab-case slugs and must not be used.
Important mismatch to resolve in the final plan: Temurbek’s live rows use seven referenced service categories, while the current canonical seed defines four consolidated categories. Mobile presentation is primarily driven by the four-tab taxonomy, so literal category cloning may not be necessary—but the team should choose deliberately.

Two bootstrap boundaries

Choose how far “ready” should go

Both options end with a usable service catalog and the same 13 active options. The difference is whether a fresh deployment must also support the shared Pricing v2 quote engine immediately.

Recommended starting scope

Service catalog bootstrap

Outcome: mobile and web can discover services, route specialized flows, and collect generic service choices.

  • Create or reconcile the agreed category rows.
  • Create or update all 23 canonical services by snake-case slug.
  • Set required has_options flags.
  • Clear service_options only after preflight succeeds.
  • Insert exactly 13 active option rows.
  • Verify counts, option ownership, order, and labels.

Excluded: pricing matrices, tier assignment, vehicle baselines, and quote-engine support data.

Expanded scope

Catalog + Pricing v2 bootstrap

Outcome: everything in Scope 1 plus the shared multiplier-based quote stack.

  • Run the complete Scope 1 catalog bootstrap first.
  • Seed 9 parts categories and 63 tier multipliers.
  • Seed 4 labor categories and 28 tier multipliers.
  • Wire services to parts and labor categories.
  • Apply service quantity classifications such as per_axle and per_wheel.
  • Optionally include the Camry baseline, vehicle tier assignments, and brake-system backfill.

Excluded unless added explicitly: the legacy Pricing v1 pricing_category_id system and unrelated customer/shop data.

Proposed implementation

How the one-command bootstrap would work

The public operator experience is one internal Convex action. Internally it performs small, ordered steps so failures are attributable and data is never deleted before dependencies are known.

Step 1 Preflight Validate confirmation, schema assumptions, seed uniqueness, and category decision.
Step 2 Catalog Upsert categories and 23 services by canonical slug.
Step 3 Options Resolve four service IDs, clear existing options, and insert 13 rows.
Step 4 Pricing Scope 2 only: seed and wire Pricing v2 dependencies in order.
Step 5 Audit Return counts, missing slugs, duplicate checks, and per-step status.

Proposed entry point

seeds/bootstrapServices:run

npx convex run seeds/bootstrapServices:run '{"confirm":"REPLACE_SERVICE_OPTIONS","includePricing":false}'

The final function name and argument shape are proposals, not implemented interfaces.

Replacement behavior

Services should be reconciled by slug, not deleted wholesale. Existing IDs may already be referenced by bookings, shops, fitments, and pricing data.

Only service_options is intentionally cleared and replaced, matching the original requirement.

Do not implement catalog replacement as “delete all services.” That would invalidate foreign-key-style Convex IDs across existing data. For a truly empty deployment the result is the same, but slug-based reconciliation remains safe when the command is accidentally aimed at a populated environment.

Guardrails

Safety and verification contract

Before any deletion

  • Require an exact confirmation string.
  • Validate all 23 seed slugs are unique.
  • Resolve the four option-owning services.
  • Fail if any required service or category cannot be resolved.
  • Record pre-run counts for the result summary.

After insertion

  • Assert exactly 23 canonical service slugs exist.
  • Assert exactly 13 option rows exist.
  • Assert option counts are 3 / 3 / 4 / 3.
  • Assert no duplicate (service_id, display_order) pair.
  • Return every step’s counts; never return only “success.”
Testing requirement: seed constants and their structural checks should be testable without connecting to Convex. A deployment smoke test belongs in the eventual implementation plan, but no live mutation is required to validate the seed definition itself.

Daniel + Temur working session

Decisions needed before implementation

  1. Scope 1 or Scope 2?
    Decide whether “ready” means service selection only or immediate Pricing v2 quote support.
  2. Four categories or Temurbek’s seven referenced categories?
    The mobile taxonomy already consolidates presentation into four tabs; the Convex category model should have one declared source of truth.
  3. Strict catalog or additive catalog?
    Should unexpected service rows cause a failure, remain untouched, or be disabled? Deleting them is unsafe on populated deployments.
  4. How much of Pricing v2 belongs in Scope 2?
    Confirm whether Camry baseline data, vehicle tier assignment, and the brake-system backfill are required or optional.
  5. What happens on a partially populated deployment?
    Choose whether existing canonical rows are always overwritten from seed values or only missing fields are filled.
  6. Where is the long-term source of truth?
    The web repository is described as canonical for Convex code; agree where the final bootstrap function is authored and how mobile receives it.
